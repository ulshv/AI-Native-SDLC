# platform-ingress Specification

## Purpose

Every platform service gets one easy address, like `https://gitea.sdlc.internal`, that works the same from the browser and from other services, even offline. Connections are always encrypted with certificates the laptop trusts, so there are no browser warnings, and that trust survives rebuilds.

## Requirements

### Requirement: Stable service names
Each user-facing platform service SHALL have one name in the `sdlc.internal` zone. This change
provides at least `gitea.sdlc.internal`, `plane.sdlc.internal` and `argocd.sdlc.internal`.

#### Scenario: Service names resolve
- **WHEN** any of the provided service names is looked up on the host
- **THEN** it resolves, and an HTTPS request to it reaches the matching service

### Requirement: Same name from host and pods
A service name SHALL reach the same service from a browser on the host and from inside any pod
in the cluster, so URLs generated by one service work for every other client.

#### Scenario: Browser on the host
- **WHEN** a browser on the host opens `https://gitea.sdlc.internal`
- **THEN** the git server's web interface loads

#### Scenario: Client inside a pod
- **WHEN** a process in any pod requests `https://gitea.sdlc.internal`
- **THEN** it reaches the same git server, and certificate validation succeeds once the local CA is trusted in that pod

### Requirement: Independent of the host network
Name resolution and access to platform services SHALL work regardless of the host's network
connection, including with no network at all and after switching networks.

#### Scenario: Host is offline
- **WHEN** the host has no network connection
- **THEN** every service name still resolves and its service is reachable from the host and from pods

#### Scenario: Host switches networks
- **WHEN** the host moves to a different network and gets a new address
- **THEN** every service name keeps working without any reconfiguration

### Requirement: HTTPS on every name
Every service name SHALL be served over HTTPS. Plain HTTP requests SHALL be redirected to HTTPS.

#### Scenario: HTTP request is redirected
- **WHEN** a client requests `http://plane.sdlc.internal`
- **THEN** it is redirected to `https://plane.sdlc.internal`

### Requirement: Locally trusted certificates
Certificates for every service name SHALL chain to a local root CA that the host's system trust
store and installed browsers trust, so no certificate warnings appear.

#### Scenario: No certificate warnings
- **WHEN** a service name is opened in a browser on the host or fetched with a command-line client without insecure flags
- **THEN** the connection succeeds without certificate warnings or errors

### Requirement: Root CA persists across rebuilds
The local root CA SHALL stay the same across cluster rebuilds until it is rotated, so trust is
set up once per host and per CA lifetime.

#### Scenario: Trust survives a rebuild
- **WHEN** the cluster is rebuilt
- **THEN** the host keeps trusting every service certificate without re-importing a CA

### Requirement: Root CA rotation before expiry
The root CA SHALL be valid for one year. When fewer than 30 days of validity remain, the bootstrap
command SHALL replace it. The host SHALL trust the new CA and stop trusting the old one without
manual steps.

#### Scenario: CA close to expiry
- **WHEN** the bootstrap command runs and the root CA expires in fewer than 30 days
- **THEN** every service certificate chains to a new root CA, and the host trusts it with no certificate warnings
- **AND** the host no longer trusts the old root CA

### Requirement: Adding a service name
Adding a new service name SHALL require only an edit to one declared list in the repository and
a re-run of the bootstrap command for host resolution.

#### Scenario: New name added
- **WHEN** a name is added to the declared list and the bootstrap command is re-run
- **THEN** the new name resolves from the host and from pods, and is covered by a trusted certificate
